# Deploying Iced_out to {{DOMAIN}}

**One folder.** The storefront and the backend live in the same directory, and
that directory is the document root. Generated by `tools/live/build-live.mjs` —
rebuild and this file is rewritten, so keep notes of your own somewhere else.

---

## The one file you edit

```
live/site/.env
```

The live MySQL credentials go in the DATABASE block near the top. Nothing else
in the deployment holds a secret, and nothing else changes when the database
does. PHP reads it on every request, so there is nothing to restart.

---

## What gets uploaded

Everything inside **`live/site/`**, into the document root of {{DOMAIN}}.

```
<document root of {{DOMAIN}}>/
│
│   ── the storefront (a static export: plain .html and assets) ──
├── index.html  404.html  men.html  women.html  cart.html  …
├── _next/  images/  textures/  pages/  account/  auth/  …
│
│   ── the backend ──
├── .env                ★ your database credentials      DENIED to the web
├── api/                the URLs the browser calls       PUBLIC, on purpose
│   └── v1/             index.php, auth/login.php, …
├── autoload.php                                         DENIED
├── composer.json                                        DENIED
├── bin/                console, worker, scheduler        DENIED
├── config/             app.php, database.php, routes/    DENIED
├── database/           iced_out_live.sql                 DENIED
├── migrations/                                           DENIED
├── seeds/                                                DENIED
├── src/                the whole application             DENIED
├── storage/            logs, cache, uploaded media       DENIED · must be writable
│
├── .htaccess           the rules that make all of the above true
├── setup.php           delete after step 5
└── robots.txt
```

### Why `api/` and the rest are different

They are the two halves of the same backend, and only one of them is meant to be
reachable:

- **`api/v1/`** is the *front door*. Every file in it is three lines long — it
  names one route and hands over. There is no logic and no secret in any of
  them. `/api/v1/auth/login` has to be a URL or the shop cannot sign anyone in.
- **everything else** (`config/`, `src/`, `storage/`, `.env`, …) is the *building*.
  `config/database.php` names your credentials, `storage/logs` holds
  password-reset codes, `src/` is the application. None of it should ever be
  fetchable, and `.htaccess` refuses all of it.

`api/v1/index.php` reaches the rest through the **filesystem** (a PHP `require`),
which no web-server rule touches. So the backend works perfectly while remaining
unreachable by URL. Denying a folder does not hide it from PHP — only from
browsers.

### The trade you are making

In this layout `.env` sits **inside the web root**, and the only thing between a
browser and your database password is `.htaccess`. It is defended three times:

1. the document root's `.htaccess` refuses `/config`, `/src`, `/storage`,
   `/database`, `/migrations`, `/seeds`, `/bin`, `/autoload.php` and
   `/composer.json` outright;
2. each of those folders carries its own deny-all `.htaccess`;
3. a rule refuses any file whose name starts with a dot, at any depth — which is
   `.env` itself.

Layer 1 lives in the same file that maps every clean URL on the site. That is
deliberate: if that file ever stops being read, `/men` and `/cart` 404
immediately, so the protection cannot fail quietly while the site still looks
fine. **Step 7 makes you check it.**

If your host lets you write above the document root, `--layout=split` puts the
backend in one folder up there instead, where no URL maps to it at all and none
of this can go wrong.

---

## 1. Create the subdomain

cPanel → **Domains** → Create A Domain → `{{DOMAIN}}`.

Note the document root it gives you — usually `/home/<cpanel-user>/{{DOMAIN}}`
or `/home/<cpanel-user>/public_html/iced-out`.

Then cPanel → **SSL/TLS Status** → run AutoSSL. The site forces https and session
cookies are marked `Secure`, so nobody can stay signed in until the certificate
is live. To look at the site before then, comment out the four
`RewriteCond`/`RewriteRule` https lines in `.htaccess`, and restore them after.

**PHP 8.2 or newer.** cPanel → **Select PHP Version**. Extensions needed:
`pdo_mysql`, `mbstring`, `openssl`, `gd`.

---

## 2. Create the database

cPanel → **MySQL® Databases**:

1. **Create New Database** — e.g. `icedout`. cPanel prefixes it: `myuser_icedout`.
2. **Add New User** — e.g. `iced`, long password. Becomes `myuser_iced`.
3. **Add User To Database** → tick **ALL PRIVILEGES**.

Keep all three. Do not create tables — step 5 does that.

---

## 3. Upload

Copy **everything inside `live/site/`** into the document root — the folder's
contents, not the folder itself. FTP, SFTP, rsync or cPanel File Manager all do.

- **Turn on Settings → Show Hidden Files (dotfiles) first.** `.htaccess` and
  `.env` are both hidden files. A missing `.htaccess` is the reason a site 404s
  on every page except the home page **and leaves the backend exposed**.
- **Replace, do not merge.** On a redeploy, delete the old site files first
  (keep `.env` and `storage/`). Merging leaves the previous build's pages in
  place, and a stale page asks for navigation payloads that only existed in the
  build it came from — which shows up as a console full of 404s on
  `__next.…/__PAGE__.txt` and looks like a server fault when it is not.

Check that `.htaccess`, `.env`, `index.html`, `api/` and `config/` are sitting
*directly* in the document root, not inside a nested `site/` folder.

If you would rather move one file than several hundred, zip `live/site` yourself
— select its contents, compress, upload, extract — but nothing in this project
produces a zip for you.

Then make three folders writable:

```
storage/logs     755   (775 if the web server runs as another user)
storage/cache    755
storage/media    755
```

---

## 4. Fill in the credentials

Edit `<document root>/.env`. Change five lines and save:

```ini
DB_HOST=localhost
DB_PORT=3306
DB_NAME=myuser_icedout
DB_USER=myuser_iced
DB_PASS=the password you set
```

`APP_URL`, `SESSION_SECRET` and `SETUP_TOKEN` are already correct. Leave them.

---

## 5. Create the schema — import one file

cPanel → **phpMyAdmin** → click **your database** in the left column → **Import**
→ **Choose File** → `database/iced_out_live.sql` → **Go**.

That file is the whole database: 88 tables, 3 views, and the starting data —
roles, permissions, store settings, 32 products with 121 variants, their stock
across 3 warehouses, 32 product photographs and one staff account. No orders, no
customers, no demo fixtures.

Select the right database first: the dump deliberately carries **no**
`CREATE DATABASE` and no `USE`, so it lands in whichever one you have selected
and does not care what cPanel prefixed the name with.

Two things about it, both of which fail *silently* if missed:

- The staff password hash is peppered with `SESSION_SECRET`. It verifies only
  against the `SESSION_SECRET` in the `.env` that shipped beside it. Do not
  re-mint that value.
- The `media_assets` rows name files under `storage/media`. Skip that folder on
  upload and every product photo 404s while the pages themselves look fine.

**Alternatives.** Both reach the same database, and both are safe to re-run —
migrations are checksummed and forward-only, seeds only fill empty registers:

```bash
# with SSH
cd <document root> && php bin/console.php migrate && php bin/console.php seed
```

```
# without SSH — the same two commands behind a URL
https://{{DOMAIN}}/setup.php?token={{SETUP_TOKEN}}
```

---

## 6. Close the door

The moment step 5 succeeds:

1. **Delete `setup.php`** from the document root.
2. Blank `SETUP_TOKEN=` in `.env`.

Either alone disables it. Do both.

---

## 7. Check it — including the part that matters

```
https://{{DOMAIN}}/                      the shop
https://{{DOMAIN}}/men                   a route that is not the home page
https://{{DOMAIN}}/api/v1/health         {"ok":true,…}
https://{{DOMAIN}}/api/v1/catalog/products   the product list, as JSON
```

`/men` catches a broken `.htaccess`: if it 404s while `/` works, the file did not
upload or `mod_rewrite` is off.

**Then confirm the backend is sealed. Do not skip this.**

```
https://{{DOMAIN}}/.env                  must be 403
https://{{DOMAIN}}/config/database.php   must be 403
https://{{DOMAIN}}/src/Kernel/Application.php   must be 403
https://{{DOMAIN}}/storage/logs/         must be 403
```

If any of them shows you file contents, **stop**. Your host is ignoring
`.htaccess`: take the site down, change the database password, and redeploy with
`--layout=split`. Anything other than 403 or 404 here is a live credential leak.

Finally, register an account and add something to the cart — that exercises the
database, the session cookie and the origin check together.

## 8. Before you take real money

- **Razorpay.** Put the **live** keys (`rzp_live_…`) into `RAZORPAY_KEY_ID` and
  `RAZORPAY_KEY_SECRET` in `.env`. The storefront reads the public key from the
  API at runtime, so **no frontend rebuild is needed** — save and reload. Left
  blank, checkout says card payments are not configured and cash on delivery
  still works.
  Confirmation runs through `POST /api/v1/checkout/payments/razorpay/verify`,
  which checks the signature on the browser's callback. **The webhook receiver of
  spec §8.32 is not built yet** — there is no `/api/v1/webhooks/…` route to point
  Razorpay at, so leave `RAZORPAY_WEBHOOK_SECRET` blank until it is. Until then a
  payment where the shopper closes the tab mid-callback needs reconciling by hand
  against the Razorpay dashboard.
- **Email.** `MAIL_DRIVER=log` writes password-reset codes into `storage/logs`
  and sends nothing. Fine for a first look, not fine once anyone else uses the
  site. Create an address in cPanel → Email Accounts and set `MAIL_DRIVER=smtp`,
  `SMTP_HOST=mail.{{DOMAIN}}`, `SMTP_PORT=465`, `SMTP_ENCRYPTION=ssl`,
  `SMTP_USER=` the full address, `SMTP_PASS=` its password.
- **The seeded staff account.** `admin@gmail.com` / `admin123`. This deployment
  exposes no console — the admin API is the separate CRM app — so it cannot be
  signed into here. Change the password before the CRM goes up.

## 9. Deploying a change

```bash
node tools/live/build-live.mjs                      # rebuild live/site
node tools/live/build-database.mjs                  # only if schema or seeds changed
```

A rebuild **never** overwrites `live/site/.env`, and carries `storage/media` and
`database/iced_out_live.sql` across untouched — it cannot lose the credentials
you typed in step 4, nor separate the photographs from the rows that name them.

- **Frontend change:** re-upload the `.html` files, `_next/`, `images/`,
  `textures/` and the route folders. Names under `_next/static` are
  content-hashed, so a stale bundle is never served — but delete the previous
  build's files rather than merging, or old routes linger.
- **Backend change:** re-upload `api/`, `src/`, `config/`, `bin/`, keeping the
  server's `.env` and `storage/`.
- **Schema change (a new migration):** run `php bin/console.php migrate` on the
  server, or put `setup.php` back for one run. **Do not re-import
  `iced_out_live.sql` on a live site** — it drops every table, orders included.
  That file is for a first install only.

## 10. When something is wrong

| Symptom | Cause |
|---|---|
| Home page fine, every other page 404 | `.htaccess` missing from the document root, or `mod_rewrite` off. Turn on Show Hidden Files and check. **Until it is there the backend is also unprotected** — see step 7. |
| `/.env` or `/config/database.php` returns its contents | The host is ignoring `.htaccess`. Treat the password as leaked: change it, and redeploy with `--layout=split`. |
| Every page redirects forever | The host terminates TLS upstream. Delete the four https lines from `.htaccess`; the `X-Forwarded-Proto` condition already covers most hosts. |
| `/api/v1/health` returns the HTML 404 page | `api/` did not upload, or `api/v1/.htaccess` is missing. |
| `"The backend was not found…"` | `autoload.php` and `config/` are not in the document root. They upload alongside the site's files, not in a subfolder. |
| `"Could not connect to MySQL…"` | The prefixed names in `.env` do not match cPanel, or the user was never added to the database with ALL PRIVILEGES. |
| Signed out on every click | The site is being served over http. Finish AutoSSL and restore the https redirect — the cookie is `Secure`. |
| Uploads or logins fail silently | `storage/` is not writable. Check `storage/{logs,cache,media}`. |
| A blank white page | PHP fatal. `APP_DEBUG=false` keeps it out of the response on purpose — read `storage/logs/app-*.log`. |
| Product tiles have no photos | `storage/media` did not upload — the rows are there, the files are not. |
| Import stops with "access denied; you need SUPER privileges" | Something re-added `DEFINER` to the views. Regenerate with `node tools/live/build-database.mjs`. |
| Import stops on a duplicate key | The database was not empty. Drop and recreate it in cPanel, then import once. |
| The admin password stopped working | `SESSION_SECRET` no longer matches the one the dump was built with — it peppers the hash. Restore the original value. |
