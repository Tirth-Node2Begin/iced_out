# Deploying Iced_out to {{DOMAIN}}

Generated by `tools/live/build-live.mjs`. Rebuild with `node tools/live/build-live.mjs`
and this file is rewritten — so put notes of your own somewhere else.

---

## The one file you edit

```
live/iced-out-api/.env
```

The live MySQL credentials go in the DATABASE block near the top of it. Nothing
else in the deployment holds a secret, and nothing else has to change when the
database does. It is read on every request, so there is nothing to restart.

---

## What is in this folder

| Folder | Where it goes on the server | Why |
|---|---|---|
| `public_html/` | the document root of **{{DOMAIN}}** | the storefront, plus `api/v1/` — everything a URL is allowed to reach |
| `iced-out-api/` | **one level above** the document root | `.env`, config, source, migrations, seeds, uploads — nothing a URL may reach |

The split is the whole security model. `public_html/api/v1/_backend.php` walks
up the directory tree looking for a folder called `iced-out-api` with an
`autoload.php` in it, so the layout below works without you editing a path:

```
/home/<cpanel-user>/
├── iced-out-api/                   ← the private half
│   ├── .env                        ← ★ credentials
│   ├── config/  src/  migrations/  seeds/  bin/
│   ├── database/iced_out_live.sql   ← the one-file import (step 5)
│   └── storage/{logs,cache,media}  ← must be writable; media holds the photos
└── public_html/
    └── iced-out/                   ← document root of {{DOMAIN}}
        ├── .htaccess  index.html  _next/  images/  …
        ├── setup.php               ← delete after step 5
        └── api/v1/                 ← PHP, but holds no secret
```

If your host will not let you write above the document root, put `iced-out-api`
inside it anyway — it ships a deny-all `.htaccess` for exactly that case — or
set `$explicit` at the top of `public_html/api/v1/_backend.php` to its absolute
path.

## 1. Create the subdomain

cPanel → **Domains** → Create A Domain → `{{DOMAIN}}`.

Note the document root it gives you. It is usually
`/home/<cpanel-user>/{{DOMAIN}}` or `/home/<cpanel-user>/public_html/iced-out`.

Then cPanel → **SSL/TLS Status** → run AutoSSL for the subdomain. The site
forces https and session cookies are marked `Secure`, so nobody can stay signed
in until the certificate is live. If you need to look at the site before then,
comment out the three `RewriteCond`/`RewriteRule` https lines in
`public_html/.htaccess`, and put them back afterwards.

**PHP 8.2 or newer** is required. cPanel → **Select PHP Version**. The
extensions needed are `pdo_mysql`, `mbstring`, `openssl`, `gd` — all four are on
by default on most hosts; tick them if they are not.

---

## 2. Create the database

cPanel → **MySQL® Databases**:

1. **Create New Database** — e.g. `icedout`. cPanel prefixes it, so the real
   name becomes something like `myuser_icedout`.
2. **Add New User** — e.g. `iced`, with a long password. Real name:
   `myuser_iced`.
3. **Add User To Database** → tick **ALL PRIVILEGES**.

Write down all three: the *prefixed* database name, the *prefixed* user, and the
password. Do not create any tables — step 5 does that.

---

## 3. Upload

Two uploads, two destinations.

Copy the CONTENTS of each folder to its destination — FTP, SFTP, rsync or
cPanel File Manager.

- `live/public_html/*` → the subdomain's document root.
- `live/iced-out-api` → `/home/<cpanel-user>/`, keeping that folder name.

Replace rather than merge on a redeploy (keep `.env` and `storage/`): a stale
page left behind asks for navigation payloads that only existed in the build it
came from, which fills the console with 404s that look like a server fault.

Make sure the extracted document root has `.htaccess` and `index.html` sitting
directly in it — not a nested `public_html/` folder. File Manager hides
dot-files until you switch on **Settings → Show Hidden Files**, and a missing
`.htaccess` is the reason a site 404s on every page except the home page.

**With SSH or FTP:** copy `live/public_html/*` (including dot-files) into the
document root and `live/iced-out-api` into the home directory.

Then set permissions on the three folders PHP writes to:

```
iced-out-api/storage/logs     755   (775 if the web server runs as another user)
iced-out-api/storage/cache    755
iced-out-api/storage/media    755
```

---

## 4. Fill in the credentials

Edit `/home/<cpanel-user>/iced-out-api/.env` — File Manager → right-click →
Edit is fine. Change these five lines and save:

```ini
DB_HOST=localhost
DB_PORT=3306
DB_NAME=myuser_icedout
DB_USER=myuser_iced
DB_PASS=the password you set
```

`APP_URL`, `SESSION_SECRET` and `SETUP_TOKEN` are already set correctly for this
deployment. Leave them.

---

## 5. Create the schema — import one file

cPanel → **phpMyAdmin** → click **your database** in the left column → **Import**
→ **Choose File** → `iced-out-api/database/iced_out_live.sql` → **Go**.

That file is the whole database: 88 tables, 3 views, and the starting data —
roles, permissions, store settings, 32 products with 121 variants, their stock
across 3 warehouses, 32 product photographs and one staff account. No orders, no
customers, no demo fixtures.

Selecting the right database first matters: the dump deliberately contains **no**
`CREATE DATABASE` and no `USE`, so it lands in whichever database you have
selected and does not care what cPanel prefixed the name with.

Two things about it, both of which fail *silently* if missed:

- The staff password hash is peppered with `SESSION_SECRET`. It verifies only
  against the `SESSION_SECRET` in the `.env` that shipped beside it. Do not
  re-mint that value, or the admin login stops working with no other symptom.
- The `media_assets` rows name files under `iced-out-api/storage/media`. Skip
  that folder in step 3 and every product photo 404s while the pages themselves
  look perfectly fine.

**Alternatives**, if you would rather not import a dump. Both end at the same
database, and both are safe to re-run — migrations are checksummed and
forward-only, and the seeds only fill registers that are empty:

```bash
# with SSH
cd ~/iced-out-api && php bin/console.php migrate && php bin/console.php seed
```

```
# without SSH — the same two commands behind a URL
https://{{DOMAIN}}/setup.php?token={{SETUP_TOKEN}}
```

## 6. Close the door

The moment step 5 reports success:

1. **Delete `public_html/setup.php`.**
2. Blank `SETUP_TOKEN=` in `iced-out-api/.env`.

Either one alone disables it. Do both.

## 7. Check it

```
https://{{DOMAIN}}/                      the shop
https://{{DOMAIN}}/api/v1/health         {"ok":true,…}
https://{{DOMAIN}}/api/v1/config/storefront
https://{{DOMAIN}}/men                   a route that is not the home page
```

The third one is the one that catches a broken `.htaccess`: if `/men` 404s but
`/` works, `.htaccess` did not upload or `mod_rewrite` is off.

Register an account and add something to the cart. That exercises the database,
the session cookie and the origin check in one go.

## 8. Before you take real money

- **Razorpay.** Put the **live** keys (`rzp_live_…`) into `RAZORPAY_KEY_ID` and
  `RAZORPAY_KEY_SECRET` in `.env`. The storefront reads the public key from the
  API at runtime, so **no frontend rebuild is needed** — save the file and
  reload. Left blank, checkout says card payments are not configured and cash on
  delivery still works.
  Payment confirmation runs through `POST /api/v1/checkout/payments/razorpay/verify`,
  which checks the signature on the browser's callback. **The webhook receiver of
  spec §8.32 is not built yet** — there is no `/api/v1/webhooks/…` route to point
  Razorpay at, so leave `RAZORPAY_WEBHOOK_SECRET` blank until it is. Until then a
  payment where the shopper closes the tab mid-callback needs reconciling by hand
  against the Razorpay dashboard.
- **Email.** `MAIL_DRIVER=log` writes password-reset codes into
  `storage/logs` and sends nothing. Fine for a first look, not fine once anyone
  else uses the site — a code in a log file is a code anyone with the log has.
  Create an address in cPanel → Email Accounts and set `MAIL_DRIVER=smtp`,
  `SMTP_HOST=mail.{{DOMAIN}}`, `SMTP_PORT=465`, `SMTP_ENCRYPTION=ssl`,
  `SMTP_USER=` the full address, `SMTP_PASS=` its password.
- **The seeded staff account.** `admin@gmail.com` / `admin123` is created by the
  seed. This storefront deployment exposes no console — the admin API lives in
  the separate CRM app — so it cannot be signed into here. Change the password
  before the CRM goes up.

## 9. Deploying a change

```bash
node tools/live/build-live.mjs              # the two folders
node tools/live/build-database.mjs          # only if the schema or seeds changed
```

A rebuild **never** overwrites `live/iced-out-api/.env`, and carries
`storage/media` and `database/iced_out_live.sql` across untouched — so it cannot
lose the credentials you typed in step 4, nor separate the product photographs
from the rows that name them. Everything else is regenerated.

- **Frontend change:** re-upload `live/public_html` (leave `api/v1` alone if the
  backend did not change). Filenames under `_next/static` are content-hashed and
  cached for a year, so a stale bundle is never served — but do delete files
  from the previous build rather than merging folders, or old routes linger.
- **Backend change:** re-upload `live/iced-out-api`, keeping the server's `.env`
  and `storage/`.
- **Schema change (a new migration):** run `php bin/console.php migrate` on the
  server, or put `setup.php` back for one run. **Do not re-import
  `iced_out_live.sql` on a live site** — it drops every table, taking the orders
  and customers with it. That file is for a first install only.

## 10. When something is wrong

| Symptom | Cause |
|---|---|
| Home page fine, every other page 404 | `.htaccess` missing from the document root, or `mod_rewrite` off. Turn on Show Hidden Files and check it is there. |
| Every page redirects forever | The host terminates TLS upstream. Delete the three https lines from `.htaccess`; the `X-Forwarded-Proto` condition already covers most hosts. |
| `/api/v1/health` returns the HTML 404 page | `public_html/api/v1/` did not upload, or its own `.htaccess` is missing. |
| `"The iced-out-api folder was not found…"` | The private half is not above the document root, or is named something else. Rename it, or set `$explicit` in `api/v1/_backend.php`. |
| `"Could not connect to MySQL…"` | The prefixed names in `.env` do not match cPanel, or the user was never added to the database with ALL PRIVILEGES. |
| Signed out on every click | The site is being served over http. Finish AutoSSL and restore the https redirect — the cookie is `Secure`. |
| Uploads or logins fail silently | `storage/` is not writable. Check `iced-out-api/storage/{logs,cache,media}`. |
| A blank white page | PHP fatal. `APP_DEBUG=false` keeps it out of the response on purpose — read `iced-out-api/storage/logs/app-*.log`. |
| Product tiles have no photos | `iced-out-api/storage/media` did not upload — the rows are there, the files are not. Upload that folder. (If you installed via seed rather than the dump, check `seeds/data/images/` has its five source sheets and re-run the seed.) |
| Import stops with "access denied; you need SUPER privileges" | Something re-added `DEFINER` to the views. Regenerate with `node tools/live/build-database.mjs`, which strips them. |
| Import stops on a duplicate key | The database was not empty. Drop and recreate it in cPanel, then import once. |
| The admin password stopped working | `SESSION_SECRET` in `.env` no longer matches the one the dump was built with — it peppers the hash. Restore the original value. |
